Hay una escena que se repite: arranca un proyecto con entusiasmo, el equipo empieza a construir y tres meses después descubren que cada quien entendía algo distinto. El retraso no se debe a que trabajaran lento, sino a que nunca se puso de acuerdo, por escrito y de forma clara, qué se iba a lograr.

Esa fase previa, a veces incómoda, es donde se ganan o se pierden la mayoría de los proyectos.

## El problema: empezar por la solución

Casi todos los proyectos nacen como una solución: "necesitamos un portal", "hay que migrar a la nube", "vamos a usar IA". Pero una solución no es un objetivo. Detrás debería haber una pregunta: ¿qué problema cambia si esto sale bien?

Un ejemplo:

- **Solución:** "Construir una app móvil para clientes."
- **Problema real:** "El 40 % de las llamadas a soporte son consultas de estado de pedido que el cliente podría resolver solo."

Con el segundo planteamiento, quizá la app es la mejor opción, o quizá bastaba un correo automático. Si no defines el problema, no puedes comparar opciones ni saber si funcionó.

## Los elementos de una buena definición

### 1. Objetivo claro y medible

Una frase que cualquier persona del proyecto pueda repetir. Si hace falta una diapositiva para explicarlo, aún no está claro. Mejor si incluye un número y una fecha: "Reducir un 30 % las consultas de estado de pedido en soporte antes de junio."

### 2. Alcance: lo que entra y lo que no

Definir lo que **no** se hará es tan importante como lo que sí. El alcance sin límites crece solo, pedido tras pedido. Una lista explícita de "fuera de alcance" te da con qué responder cuando alguien dice "ya que estamos, ¿podrías también…?".

### 3. Criterios de éxito

Responde: ¿cómo sabremos que terminamos y que valió la pena? Distingue entre:

- **Entregables:** lo que se produce (un sistema, un informe).
- **Resultados:** el cambio que provoca (menos llamadas, menos errores).

Un proyecto puede entregar todo lo prometido y fracasar en resultados.

### 4. Quiénes están involucrados

Identifica al patrocinador (quien pone el respaldo y los recursos), a las personas que usarán el resultado, al equipo y a quienes pueden bloquearlo. Cada grupo necesita algo distinto de ti.

### 5. Restricciones y supuestos

Las restricciones son límites conocidos: presupuesto, fecha, personal disponible. Los supuestos son cosas que das por ciertas sin haberlas confirmado: "el proveedor entregará la API en marzo". **Los supuestos no escritos son los riesgos más peligrosos**, porque nadie los vigila.

## El triángulo y sus incómodas decisiones

Alcance, tiempo y costo se afectan entre sí. Si alguien exige más alcance en menos tiempo con el mismo presupuesto, algo tiene que ceder, y casi siempre lo que cede es la calidad, sin que nadie lo haya decidido.

Pregunta desde el inicio: **¿cuál de los tres es el menos flexible?** Si la fecha es fija (un evento, una normativa), entonces el alcance es lo que se negocia. Tener esa conversación pronto evita sorpresas.

## Una plantilla breve

Antes de arrancar, intenta llenar una página con:

| Pregunta | Tu respuesta |
|---|---|
| ¿Qué problema resolvemos y para quién? | |
| ¿Cómo medimos el éxito? | |
| ¿Qué incluye y qué no? | |
| ¿Quién es el patrocinador y quién decide? | |
| ¿Qué supuestos estamos haciendo? | |
| ¿Cuál es la restricción más rígida? | |
| ¿Cuáles son los 3 riesgos principales? | |

Si no puedes responder alguna, ya encontraste dónde se va a torcer el proyecto, y encontrarlo hoy es barato.

## Errores comunes

- **Aprobar sin leer.** El patrocinador firma una definición que nunca revisó con cuidado, y después discute el alcance.
- **Definición enorme que nadie lee.** Una página clara vale más que cuarenta ambiguas.
- **Tratar la definición como inamovible.** Debe poder cambiar, pero a través de un acuerdo explícito, no por deslizamiento.
- **Saltarse a los usuarios.** Si nunca hablas con quien usará el resultado, estás adivinando.

## Para finalizar

Definir el proyecto no es burocracia: es el momento más barato para equivocarte. Una página honesta con objetivo, alcance, éxito, supuestos y riesgos hace que todos jalen hacia el mismo lado.
